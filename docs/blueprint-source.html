The question

A regular-season ticket has weeks on sale and a known opponent. A postseason ticket can go on sale before the game exists (“Game 5, if necessary”), change opponent overnight, and vanish when a series ends early. How does the market price that uncertainty, and where does that leave money on the table for the club?

Why it matters to a team

Postseason inventory is the highest-margin ticketing a club sells all year, and the one it has the least time to price. Every Strategy & Analytics group in the league watches the resale market in October. This project does what they do, on public data, and writes it up the way they would.

What gets built

  • An hourly data pipeline (Python → GitHub Actions → CSV → SQLite) that runs unattended for five weeks
  • A SQL analysis layer: pacing, price curves, primary-vs-resale gap, series-state effects
  • A regression that puts a number on the “if necessary” discount and the series-state premium
  • A Tableau Public dashboard (4 views) and a one-page memo written for a VP of Ticketing
  • A public GitHub repo with a README a hiring manager can read in three minutes

Design decisions you should be able to defend

DecisionWhy
Hourly, not dailyPostseason games are on sale for 2–7 days. A daily snapshot gives 3 points per game; hourly gives 70+. The price curve only exists at this resolution.
All 12 teams, not just the YankeesIf the Yankees lose in three, a NY-only project is dead on Oct 1. League-wide, elimination is a finding, not a failure. Also gives ~45 games instead of 3.
CSV in git, not a database on a serverFree, auditable, reproducible by anyone who clones the repo. Recruiters can see the data grew hour by hour. SQLite is rebuilt from the CSVs on demand.
Two sources, not oneResale alone shows demand. Primary alone shows the club’s guess. The gap between them is the business question.
Giants/Jets in the backgroundSame scraper, different query, zero marginal cost. Becomes the December extension (a 12-week NFL price curve with a same-stadium control).
Regex on titles for “postseason”Neither API has a clean postseason flag. Titles do (“ALDS”, “Home Game 2”). Pragmatic, documented in code, and a good interview story about messy real data.

Known limits (say these before anyone asks)

  • Listings, not sales. SeatGeek stats describe what’s asked, not what cleared. Listing count falling is the best available proxy for sales.
  • Aggregates, not sections. Lowest/average/highest across the whole building. Section-level data isn’t public. Say so, then note what the club could do with its own Archtics data.
  • Fees. Ticketmaster priceRanges may or may not include fees (the price_type field says). Compare like with like.
  • Scheduled runs can drift. GitHub may delay a cron by minutes. We store the true captured_at and compute hours-to-game from it, so drift is harmless.
  • Time-TBD games. Before a series is set, games carry placeholder times. The time_tbd flag lets us exclude or study them.

Why the bracket is data

Every series outcome is an event in the dataset. When the Yankees win Game 1, the Game 3 “if necessary” listing either firms up or evaporates. When a series ends in a sweep, an entire game’s worth of listings goes to zero. The tracker column on the left is your annotation layer: what you noticed as a fan becomes the caption on the dashboard.

Watch for these moments

  • Sweep. Game 3 listings the morning after a 2–0. How fast do sellers cut?
  • Forced Game 5 / Game 7. The scarcest ticket of the round. Price vs. Game 1 of the same series.
  • Opponent revealed. The 1-seed’s Game 1 listing exists before the opponent is known. Does the price move when it is?
  • Yankees–Red Sox. Rivalry premium: compare to the other three Wild Card hosts at the same hours-to-game.
  • Weather. A postponement is a natural experiment on “time to game.”

Data dictionary · what one row means

A hiring manager’s first question about any dataset is “what’s the grain?” Answer: one row per game per hour per source. Everything below hangs off that.

The one file you maintain by hand

data/results.csv · one row per game · columns: series, game_no, date, home, away, played (1/0), home_w_before, home_l_before, winner, note. Fill it from the bracket page after each game. It’s tiny (≤45 rows), and it’s what turns a price log into an event study. Recruiters like seeing a human-curated dimension table next to machine-collected facts; it shows you know the difference.

Findings template · write the sentence before you have the number

One sentence, one number, one comparison. Draft with blanks on Oct 9, fill on Nov 1. If the data disagrees with you, that’s a better finding, not a failure.

The model · one regression, explained in dollars

Q7 from the analysis plan: the part that separates “I made a dashboard” from “I can tell you what drives price.” One model, every choice defended, every coefficient translated into a ticket.

The regression, sketched

import pandas as pd, numpy as np, sqlite3
import statsmodels.formula.api as smf

con = sqlite3.connect("data/pricing.db")
df = pd.read_sql("""
  SELECT r.*, s.home_w_before AS w,
         s.home_l_before AS l, s.played
  FROM resale r
  LEFT JOIN results s
    ON s.home = r.home_team AND s.date = date(r.datetime_local)
  WHERE r.bucket = 'mlb_postseason'
    AND r.hours_to_game BETWEEN 1 AND 168
""", con)

df["log_p"]  = np.log(df.median_price)
df["log_h"]  = np.log(df.hours_to_game)
df["ifnec"]  = df.title.str.contains("If Necessary").astype(int)
rounds = r"(Wild Card|ALDS|NLDS|ALCS|NLCS|World Series)"
df["round"]  = df.title.str.extract(rounds)
nyy = df.home_team.eq("New York Yankees")
bos = df.away_team.eq("Boston Red Sox")
df["rival"]  = (nyy & bos).astype(int)

m = smf.ols("log_p ~ log_h + C(round) + ifnec + rival + w + l",
            data=df).fit(cov_type="cluster",
                         cov_kwds={"groups": df.event_id})
print(m.summary())
# ifnec = -0.35  →  "if necessary" listings ~30% cheaper, all else equal

How to read a coefficient out loud

On a log-price model, a coefficient of −0.35 on ifnec means an “if necessary” listing is about 30% cheaper than a guaranteed game in the same round at the same hours-to-game (e−0.35 ≈ 0.70). Say it that way in the memo. Never say “statistically significant” without saying what the number means for a ticket.

What makes this more than a class project

  • Clustered standard errors by game. 70 hourly rows of one game aren’t 70 independent observations. Knowing that is the difference between a BA student and an analyst.
  • Log-log on hours. Turns “price falls as the game nears” into an elasticity a pricing manager can use.
  • A hand-built dimension (series state). Shows you understand data modeling, not just querying.
  • Limits stated first. Listings ≠ sales; building-level aggregates; one postseason. Then the recommendation anyway.

Variables, and why each one is in

VariableDefinitionWhy it belongs · what you expect
log_hlog(hours to first pitch)Time-to-event is the dominant driver of resale prices. Log form makes the coefficient an elasticity: “a 10% cut in time left moves price X%.” Expect negative.
C(round)Wild Card / DS / LCS / WSStakes rise by round. Fixed effects absorb that so the other coefficients aren’t just “the World Series is expensive.” Expect monotonic increase.
ifnec1 if the title says “If Necessary”The project’s headline variable: the uncertainty discount. Expect −0.2 to −0.5 (20–40% cheaper).
rival1 for Yankees–Red SoxThe rivalry premium, controlled for round and time. Expect positive; the size is the finding.
w, lHome team’s series wins / losses before this gameSeries state. A team down 0–2 hosting Game 3 is a different product than one up 2–0. Expect w positive, l negative, and larger in magnitude late in the series.

Checks you run before you believe it

  • Plot residuals vs hours_to_game: if there’s a curve, add log_h².
  • Drop the World Series and re-fit: do the signs hold?
  • Swap median for lowest price: same story?
  • Cluster by game (done) and by series: do the standard errors change much?

What you say if someone asks “why not machine learning?”

“The goal was a number a pricing manager can act on, not the best predictor. Log-linear gives an interpretable elasticity and a clean uncertainty discount. For a forecast I’d try the same features in a gradient-boosted model and compare out-of-sample error.” That answer gets you hired more often than a random forest does.

-- Q1: get-in price by hours-to-game bucket, by round
SELECT CASE WHEN title LIKE '%Wild Card%' THEN 'WC'
            WHEN title LIKE '%LDS%'       THEN 'DS'
            WHEN title LIKE '%LCS%'       THEN 'LCS'
            WHEN title LIKE '%World Series%' THEN 'WS'
       END AS round,
       CASE WHEN hours_to_game > 48 THEN '48h+'
            WHEN hours_to_game > 24 THEN '24-48h'
            WHEN hours_to_game > 6  THEN '6-24h'
            ELSE '0-6h' END AS bucket,
       COUNT(*) AS n, ROUND(AVG(lowest_price)) AS avg_get_in
FROM   resale

-- Q2: Yankees-Red Sox vs the other three WC hosts, same hour
SELECT a.captured_at,
       a.lowest_price                       AS nyy,
       ROUND(AVG(b.lowest_price))           AS others,
       ROUND(a.lowest_price / AVG(b.lowest_price), 2)
         AS ratio
FROM   resale a
JOIN   resale b
  ON   b.captured_at = a.captured_at
 AND   b.title LIKE '%Wild Card%'
 AND   b.home_team <> a.home_team
WHERE  a.home_team = 'New York Yankees'
  AND  a.title LIKE '%Wild Card%Game 1%'
GROUP  BY a.captured_at ORDER BY 1;
-- Q5: primary vs resale gap, per game, latest snapshot
SELECT s.home_team, date(s.datetime_local) AS game_date,
       t.min_price                          AS club_floor,
       s.lowest_price                       AS market_floor,
       ROUND(100.0 * (s.lowest_price - t.min_price)
             / t.min_price, 1) AS gap_pct
FROM   resale s
JOIN   ticketmaster t
  ON   t.local_date = date(s.datetime_local)
 AND   t.name LIKE '%' || substr(s.home_team,
                 instr(s.home_team,' ')+1) || '%'
 AND   substr(t.captured_at,1,13)
     = substr(s.captured_at,1,13)
WHERE  s.captured_at = (SELECT MAX(captured_at)
                        FROM resale)
ORDER  BY gap_pct DESC;

Week of Oct 19 · CTEs

-- Q3: "if necessary" discount vs Game 1, matched on hours
WITH g AS (
  SELECT event_id, home_team, title,
         title LIKE '%If Necessary%'        AS ifnec,
         CAST(hours_to_game AS INT) / 6 * 6 AS h6, -- 6h bins
         median_price
  FROM   resale WHERE hours_to_game BETWEEN 1 AND 72
),
g1 AS (
  SELECT home_team, h6, AVG(median_price) AS p_game1
  FROM   g WHERE title LIKE '%Game 1%' GROUP BY 1, 2
)
SELECT g.home_team, g.h6,
       ROUND(AVG(g.median_price)) AS p_ifnec,
       ROUND(g1.p_game1)          AS p_game1,
       ROUND(100.0 * (AVG(g.median_price) - g1.p_game1)
             / g1.p_game1, 1) AS discount_pct
FROM   g JOIN g1 USING (home_team, h6)
WHERE  g.ifnec = 1
GROUP  BY 1, 2 ORDER BY 1, 2;

Week of Oct 26 · window functions

-- Q6: sell-through velocity: listings vs 24h earlier
WITH w AS (
  SELECT event_id, home_team, captured_at, hours_to_game,
         listing_count, median_price,
         LAG(listing_count, 24) OVER (PARTITION BY event_id
             ORDER BY captured_at) AS lc_24h_ago,
         LAG(median_price, 1) OVER (PARTITION BY event_id
             ORDER BY captured_at) AS p_prev
  FROM   resale
)
SELECT home_team, captured_at,
       listing_count - lc_24h_ago AS listings_delta_24h,
       ROUND(100.0 * (median_price - p_prev) / p_prev, 2)
         AS price_chg_pct,
       RANK() OVER (PARTITION BY substr(captured_at,1,10)
                    ORDER BY listing_count - lc_24h_ago)
         AS fastest_seller_today
FROM   w
WHERE  lc_24h_ago IS NOT NULL
ORDER  BY captured_at DESC, fastest_seller_today;
-- Q4: Game 2 price before/after the Game 1 result
WITH r AS (
  SELECT s.*, x.winner = x.home AS home_won
  FROM   resale s
  JOIN   results x
    ON   x.home = s.home_team AND x.game_no = 1
   AND   s.title LIKE '%Game 2%'
), t AS (
  SELECT home_team, home_won,
         AVG(CASE WHEN hours_to_game BETWEEN 26 AND 28
                  THEN median_price END) AS before_g1,
         AVG(CASE WHEN hours_to_game BETWEEN 14 AND 16
                  THEN median_price END) AS after_g1
  FROM   r GROUP BY 1, 2
)
SELECT home_won, COUNT(*) AS series,
       ROUND(AVG(100.0 * (after_g1 - before_g1) / before_g1), 1)
         AS avg_move_pct
FROM   t GROUP BY 1;

Save each under analysis/ with the question and, later, the answer as a comment. That folder is what you walk a hiring manager through.
